# GEO 诊断

## 概述

用于发起 AIDSO GEO 品牌诊断，并返回最终诊断报告。

1. 用户输入品牌诊断请求
2. 系统先获取品牌的推荐诊断问题
3. 用户可对推荐问题进行确认或修改
4. 问题确认完成后，再正式发起诊断
5. 诊断完成后返回最终结果

---

## 支持的触发方式

- 帮我做一个 XX 的 GEO 诊断报告
- 生成 XX 的 GEO 诊断报告
- 查一下 XX 的 GEO 表现

---

## 品牌提取规则

当用户输入类似以下表达时，需要从中提取 `brandName`：

- 帮我做一个**露露**的GEO诊断报告
- 做一个**欧莱雅**的GEO诊断报告
- 生成**XX品牌**的GEO诊断报告

### 建议提取规则

可按以下模式识别品牌名称：

- `帮我做一个(.+?)的GEO诊断报告`
- `做一个(.+?)的GEO诊断报告`
- `生成(.+?)的GEO诊断报告`
- `(.+?)的GEO诊断报告`

> ⚠️ 不要自行纠正品牌名，不要把数据外品牌名映射成其他别名。  
> 用户输入什么品牌，就传什么品牌。

---

## 问题交互规则

正式诊断前，系统需要先为该品牌获取推荐诊断问题。

### 交互目标

- 让用户知道当前诊断将围绕哪些问题展开
- 允许用户在正式诊断前调整问题
- 避免直接对不合适的问题发起诊断

**系统支持两种处理方式**

1. 用户确认推荐问题
   如果用户认可系统返回的问题列表，则可直接确认，进入正式诊断流程。

2. 用户修改推荐问题
   如果用户不认可推荐问题，则可以修改问题，系统应以用户最终确认的问题为准发起诊断。

---

## 推荐问题接口

### 接口地址

```
POST https://api.aidso.com//openapi/skills/get_questions
```

### 请求头

```
x-api-key: {用户已绑定的_api_key}
```

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
|----|----|----|----|
| `brand_name` | string | 是 | 要诊断的品牌名称 |

### 成功返回示例

```
{
    "code": 200,
    "msg": "成功",
    "data": [
        "哪个品牌的智能手机性价比高？",
        "哪款笔记本电脑性能好？",
        "平板电脑哪个牌子好用？",
        "智能手表买什么品牌好？",
        "智能家居品牌排名前十的有哪些？"
    ]
}
```

### 推荐问题返回后的交互规则

当系统拿到推荐问题后，应先展示给用户，再等待用户确认或修改。

**推荐展示模板**

> 已为 「{brandName}」生成推荐诊断问题：
> 
> 1. "{qustion_1}"
> 2. "{question_2}"
> 3. "{question_3}"
>
> 你可以：
> - 直接回复"确认"使用这些问题
> - 直接发送修改后的问题列表

### 用户修改规则

若用户未确认，而是直接输入新的问题内容，则视为用户修改问题。

**修改后的问题处理规则**

- 以用户最终输入的问题为准
- 不再强制使用系统推荐问题
- 用户可输入 1 个或多个问题
- 修改后的问题确认完成后，再进入积分确认流程

**推荐提示文案**

> 已收到你修改后的问题，接下来将基于这些问题发起诊断。

---

## 积分确认规则

正式发起品牌诊断前，必须先根据最终确认的问题数计算实际消耗积分。

### 计算规则

实际消耗积分数 = 问题数 × 4

### 说明

- 问题数以用户最终确认的问题列表为准
- 若用户使用系统推荐问题，则按推荐问题的最终数量计算
- 若用户修改问题，则按修改后的最终问题数量计算
- 用户未确认前，不要调用正式诊断接口

### 提示文案：

> 本次诊断共确认 {question_count} 个问题，预计消耗 {points} 积分，是否确认？

---

## 诊断发起流程

### 步骤1：检查 API Key

若未绑定，则先进入 API key 绑定流程。

### 步骤2：提取品牌名

从用户请求中识别品牌名，并保存为当前待诊断品牌。

### 步骤3：获取推荐问题

调用推荐问题接口，返回系统建议的诊断问题列表。

### 步骤4：用户确认或修改问题

- 用户确认：使用推荐问题
- 用户修改：使用用户最终输入的问题

### 步骤5：提示积分确认

向用户提示：

> 本次诊断共确认 {question_count} 个问题，预计消耗 {points} 积分，是否确认？

### 步骤6：用户确认后发起诊断

调用正式诊断接口

## 品牌诊断接口

### 接口地址

```
POST https://api.aidso.com//openapi/skills/band_report/md/v2
```

### 请求头

```
x-api-key: {用户已绑定的_api_key}
```

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
|----|----|----|----|
| `brand_name` | string | 是 | 要诊断的品牌名称 |
| `questions` | array | 是 | 要诊断的问题 |

---

## 接口返回处理规则

**成功并返回下载地址**

```
{
  "code": 200,
  "msg": "success",
  "data": "https://tcdn.aidso.com/skills/md/xxx.md"
}
```

**处理中**

```
{
  "code": 200,
  "msg": "处理中请稍后",
  "data": "3603f2bc691e4cc09f9089971f0d0380"
}

**参数错误**

```
{
  "code": 401,
  "msg": "invalid token",
}
```

**积分不足**

```
{
  "code": 401,
  "msg": "积分不足",
}
```

**没有品牌名称**

```
{
    "code": 405,
    "msg": "没有品牌名称,请传入参数{brandName}",
    "data": ""
}
```

## 自动轮询规则

当品牌诊断接口返回“处理中请稍后”时，应进入自动轮询流程。

### 轮询频率

- 每 1 分钟轮询一次

### 最长轮询时间

- 最长 30 分钟
- 即最多轮询 30 次

### 推荐执行方式

使用辅助脚本执行轮询：

```
python3 scripts/diagnosis_poll.py "{brandName}"
```

### 轮询方式

继续调用同一个诊断接口：

```
POST https://api.aidso.com//openapi/skills/band_report/md/v2
x-api-key: {api_key}
```

### 轮询结束条件

**成功**

JSON中返回有效文件链接

**失败**

不满足以下任一条件即停止轮询并返回错误"msg"：

- JSON中返回有效文件链接
- 处理中

**超时**

若超过 30 分钟仍未完成，回复：

> 诊断结果暂未生成完成，请稍后请求获取结果。
> 也可以前往官网查看：https://geo.aidso.com/completeAnalysis

---

## 手动继续查询规则

除自动轮询外，也支持用户手动查询当前待诊断品牌结果。

以下表达可视为继续查询：

- 继续
- 查看结果
- 查询结果
- 查询报告

### 执行规则

- 若当前存在待诊断品牌，则继续调用同一个诊断接口查询
- 若当前不存在待诊断品牌，则提示用户重新发起品牌诊断请求

推荐提示文案：

> 当前没有待查询的诊断任务，请重新发起品牌诊断请求。

---

## 返回结果处理规则

接口返回的是 Markdown 链接

- 直接返回 Markdown 链接
- 拉取 Markdown 内容并返回

> ⚠️ 成功返回后，必须将接口返回的 Markdown 链接 **原样返回给用户**。  
> 不要擅自修改、拆分、补充、重组、润色接口返回的任何内容。
