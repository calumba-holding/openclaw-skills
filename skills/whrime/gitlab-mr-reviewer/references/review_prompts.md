# MR 审查维度参考指南

这些是五个审查维度的**参考框架**，不是固定模板。AI 审查时应根据代码实际情况自主判断关注点、深度和顺序，这里只是提供思考方向。

---

## 如何使用这份指南

- 每个维度列出的是**值得关注的问题类型**，不是必须逐条检查的清单
- AI 应根据文件类型、变更性质、风险等级自主决定哪些维度最相关
- 同一段代码可能同时涉及多个维度，合并成一条评论比分开发五条更有价值
- 置信度低时，优先提问而不是断言

---

## 维度一：逻辑正确性 (Logic)

**核心问题：这段代码做的事情是否符合预期？**

值得关注的方向：
- 边界条件和极端值（空集合、null、零、最大值、负数）
- 条件分支是否覆盖所有情况，有无遗漏的 else 路径
- 循环终止条件，off-by-one 错误
- 状态机转换是否完整，有无非法状态
- 异步/并发场景下的竞态条件
- 错误路径下的资源释放（文件句柄、数据库连接、锁）
- 返回值是否被正确处理，忽略错误码的情况

**AI 自主判断提示：** 如果看不懂某段逻辑的意图，先问作者，不要猜测后断言有 bug。

---

## 维度二：安全性 (Security)

**核心问题：这段代码是否引入了可被利用的漏洞？**

值得关注的方向：
- 用户输入进入 SQL/命令/HTML/文件路径前是否经过验证或参数化
- 硬编码的密钥、密码、token、内部 URL
- 认证和授权检查的位置（是否在操作执行前完成，而不是之后）
- 日志中是否包含敏感数据（密码、PII、token）
- 文件上传的类型和大小限制
- 加密算法选择（MD5/SHA1 用于密码哈希是错误的）
- JWT/Session 的过期验证
- 依赖库的已知 CVE

**AI 自主判断提示：** 安全问题的严重程度取决于数据流，同样的模式在内部工具和公开 API 中风险完全不同。

---

## 维度三：架构合理性 (Architecture)

**核心问题：这个设计决策在这个代码库里是否合适？**

值得关注的方向：
- 职责划分是否清晰，有无跨层调用（如 controller 直接操作数据库）
- 是否引入了不必要的耦合，或破坏了现有的抽象边界
- 新增的抽象是否有必要，还是过度设计
- 接口设计是否对调用方友好，参数数量和类型是否合理
- 是否重复实现了已有的工具函数或库
- 配置和硬编码的边界（什么应该可配置，什么不需要）
- 对现有模块的修改是否保持向后兼容

**AI 自主判断提示：** 架构问题通常需要了解整个项目背景，不确定时标注为 suggestion 而非 critical。

---

## 维度四：代码质量 (Quality)

**核心问题：这段代码六个月后还容易维护吗？**

值得关注的方向：
- 命名是否准确表达意图（变量名、函数名、类名）
- 函数长度和嵌套深度（超长函数通常意味着职责不单一）
- 重复代码（DRY 原则，但不要为了 DRY 引入不必要的抽象）
- 魔法数字和魔法字符串（应该用有名字的常量）
- 注释是否解释了"为什么"而不是"做了什么"
- 错误信息是否对调用方有意义
- 类型标注的完整性（TypeScript any、Python 无类型注解）
- 遗留的 TODO/FIXME 是否有对应 Issue

**AI 自主判断提示：** 质量问题通常是 suggestion 级别，不要因为命名不够好就 block 一个 MR。

---

## 维度五：测试与文档 (Testing & Docs)

**核心问题：新增的代码是否有足够的测试覆盖，关键行为是否有文档？**

值得关注的方向：
- 新功能是否有对应的单元测试
- 测试是否覆盖了边界条件和异常路径，而不只是 happy path
- Mock 是否准确反映了真实依赖的行为
- 测试命名是否清晰描述了被测行为（`test_user_login_with_expired_token_returns_401`）
- 公共 API 是否有文档注释（参数、返回值、异常）
- 破坏性变更是否有迁移说明
- README 或 CHANGELOG 是否需要更新

**AI 自主判断提示：** 测试覆盖率不是唯一指标，一个测试了错误行为的测试比没有测试更危险。

## Finding 输出格式参考

AI 输出 finding 时建议包含以下字段，但格式可以根据情况灵活调整：

```json
{
  "file_path": "src/auth/token_service.py",
  "line": 47,
  "severity": "critical",
  "dimension": "security",
  "title": "JWT token expiration not validated",
  "description": "The code decodes JWT but never checks the 'exp' claim, allowing expired tokens to be accepted indefinitely.",
  "suggestion": "Add: if payload.get('exp', 0) < time.time(): raise TokenExpiredError()",
  "confidence": 0.95
}
```

- `severity`: critical / high / medium / low / suggestion
- `confidence`: 0-1，低于 0.6 时优先考虑提问而不是断言
- `suggestion` 是可选的，有具体修复方案时才写，不要为了填字段而写废话

---

## 跨维度问题的处理

一个问题可能同时涉及多个维度，例如：
- 未验证的用户输入传入 SQL → security + logic
- 过长的函数包含复杂业务逻辑 → quality + logic

这种情况下，选择**最主要的维度**标注，在 description 中说明其他影响，不要拆成多条重复评论。
